# Workbench, public demo, and quality policy

## Page map

Before this change, the private workbench had the correct six top-level pages, but each
page rendered its sections in one continuous body. The public app exposed Overview, Ask,
Architecture, Evaluation, and Safety tabs.

The private page map is now:

| Page | Lazy tabs |
| --- | --- |
| Chat | Conversation; Evidence; Quality & Cost |
| Request Inspector | Overview; Retrieval & Reranking; Context & Prompt; Generation; Quality Gate; Trace & Cost |
| Evaluations | Overview; Run Evaluation; Results & Scores; Individual Judge Calls; Evaluation Inputs; Compare Runs |
| Lineage & Index | Active Index; Documents & Lineage; Ingestion History; Generations |
| Drift & Regression | Quality Trends; Baselines; Regressions; Alerts |
| Operations | Health; Models & Budgets; Jobs & Logs; Privacy & Retention; Configuration |

Streamlit 1.63 provides stateful tabs through `key`, `on_change="rerun"`, and
`TabContainer.open`. The workbench renders only the selected tab. Stable session-state
keys preserve request, run, case, metric, and provider-call selections. A tab change or
refresh has no inference action; generation and evaluation remain behind explicit buttons.

The public app is now one narrow, responsive conversation surface with example questions,
an answer, compact source cards, and an optional production-details expander. It has no
workbench navigation, evaluation action, judge artifact, private trace/run identifier,
ingestion control, or index mutation control.

## Existing behavior and side effects

| Area | Behavior | Side effect class |
| --- | --- | --- |
| Request/evaluation/trace report readers | Read bounded process state or stored JSON/MLflow metadata | Read only |
| Retrieval and drift metric summaries | Calculate locally from stored metadata | Local calculation |
| Chat generation | Managed retrieval/reranking plus one Bedrock generation; STRICT adds one blocking GPT-OSS groundedness decision | Paid provider call(s); explicit action only |
| MLflow GenAI/RAGAS evaluation | Runs selected judge backends on reviewed PUBLIC cases | Potential paid calls; explicit action only |
| Warm-up and preflight | Loads local models or checks service/configuration availability | Resource/diagnostic action; explicit button |
| Managed indexing/publication/restoration | CLI-only | Index/database mutation; absent from both UIs |
| Evaluation report writer | Writes metadata-only safe reports after an explicit run | Local file write |
| Private judge I/O capture | Writes bounded, redacted, owner-only, expiring reviewed-PUBLIC artifacts | Opt-in private file write |
| Private artifact delete/purge | Deletes selected or expired private artifacts | Explicit destructive action |

Historical content that was not captured remains unavailable. It is never regenerated by
opening a page, tab, trace, or report.

## Runtime quality-policy flow

```text
request
  -> retrieve and assemble approved final context
  -> pre-generation evidence answerability check
       -> insufficient / unavailable relevance: controlled ABSTAIN; skip generation and judge
  -> generation
  -> deterministic authorization / evidence / visible citation / schema / PII checks
  -> STANDARD: deliver only when deterministic decision is PASS
  -> STRICT: deterministic PASS, then configured reference-free judge
       -> PASS: deliver
       -> FAIL / timeout / unavailable / error: configured FAIL, ABSTAIN, or REVIEW_REQUIRED
  -> optional asynchronous monitoring after delivery
       -> sampled + approved data handling + bounded concurrency/spend
       -> observation cannot change the already-made delivery decision

reviewed dataset
  -> EVALUATION profile
  -> deterministic retrieval metrics
  -> reference-free answer metrics
  -> reference-dependent metrics only when a reviewed reference exists
  -> metadata-only reports/traces; optional separate expiring judge-I/O artifact
```

`PASS`, `FAIL`, `ABSTAIN`, `REVIEW_REQUIRED`, `NOT_RUN`, `NOT_APPLICABLE`, `UNAVAILABLE`,
and `ERROR`
are first-class statuses. A missing or failed judge never becomes `PASS`. A policy decision
is distinct from a score, and neither an LLM score nor citation linkage guarantees factual,
financial, legal, or regulatory correctness. The policy has a configured high-risk
controlled-response/review route, but the serving entrypoints do not yet classify requests as
high risk.

Policy versions, timeouts, budgets, and behaviors live in `config/config.yaml`. They are not
universal production thresholds and require calibration against reviewed cases and human
feedback.

### Exact STANDARD runtime inventory

The serving entrypoints actually execute these controls:

- Input/access: trim and reject an empty question; enforce the configured character limit;
  require the managed runtime and pinned generation; enforce the public inference switch,
  window rate limit, and concurrency limit; redact detected input PII; retrieve with an
  anonymous `AccessContext`; apply ACL and PII filters; and reject returned chunks unless they
  remain `PUBLIC`, have no allowed groups, and contain no detected PII.
- Retrieval/evidence: require at least one final context chunk. Before generation, require at
  least one approved final passage to meet the configured cross-encoder reranker boundary.
  After generation, require at least one visible `[C#]` reference when configured and require
  every visible reference to resolve to the final context citation catalogue. This establishes
  deterministic linkage only; the separate STRICT judge evaluates semantic support.
- Output: require a non-empty answer; deterministically redact output PII and verify that the
  redacted answer has no remaining detected PII; then apply the selected policy before
  `RAGPipeline.answer()` sets outputs or returns.

The following fields exist in the typed deterministic policy but are not yet independently
derived by the serving entrypoints: `user_authorized` and `corpus_authorized` are set after the
fixed managed/PUBLIC boundary succeeds; full-response safety, timeout, and total-budget facts
are not supplied and therefore display `NOT_RUN`; and `high_risk_financial` remains `False`
because no runtime classifier is installed. These are extension points, not claims of
implemented safety, request-budget, request-timeout, or high-risk classification. The STRICT
judge retains its independently enforced timeout and cost budget.

The answerability policy `cross-encoder-reviewed-fixture-candidate-v1` currently uses a raw
reranker boundary of `0.0` and allows a partially answerable request to proceed when at least
one final approved passage clears it. That candidate boundary was chosen after inspecting the
available reviewed local evidence: a supported reviewed request had a best score of `8.75`,
while the recorded airplane/consumer-finance mismatch had a best score of `-9.4375`. It is not
a universal cutoff and must be recalibrated against a larger reviewed set before broader use.

For STANDARD, a deterministic failure is `FAIL` and the candidate is withheld. For STRICT,
judge `FAIL` is withheld; `UNCERTAIN` is recorded as `UNAVAILABLE`; timeout maps to configured
`ABSTAIN`; provider/output errors and missing usage/pricing map to the configured
`REVIEW_REQUIRED` or fail-closed result. A disabled or missing STRICT judge is
`UNAVAILABLE` internally and can never release an answer. The EVALUATION profile is rejected
from live delivery as `NOT_RUN`/`REVIEW_REQUIRED` and remains an explicit offline workflow.

## What runs when

Every normal request runs the existing PUBLIC-only ACL/PII controls, retrieval, and the bounded
answerability decision. An answerability abstention occurs before generation and therefore
before any STRICT judge call. Otherwise the request runs generation, output redaction, and the
configured pre-response deterministic policy. STANDARD does not call a paid judge. STRICT is
eligible for one configured
reference-free synchronous GPT-OSS adapter only when enabled. It receives the question,
candidate answer, and the exact `prompt_section_text` passages supplied to Gemma, including
their truncation and citation/chunk/document IDs. It does not use a reference answer or the
dataset-evaluation pipeline. The candidate is not returned by `RAGPipeline.answer()` until the
gate passes.

The candidate STRICT threshold is `0.80` in `strict-groundedness-candidate-v1`. It is a typed,
versioned calibration candidate, not a universal production truth. An explicit contradiction,
material unsupported claim, `FAIL`, or `UNCERTAIN` result cannot be overridden by the numeric
score. Input/output token caps, zero default retries, an eight-second timeout, and a USD 0.01
worst-case request budget are configured independently. Missing pricing or usage cannot become
zero or PASS.

At the offline policy boundary, the reviewed fixture set at `0.80` produces zero false passes
and zero false rejections: grounded `0.94` passes; unsupported `0.42`, contradiction `0.10`,
valid-ID-but-unsupported `0.95`, and partial/materially unsupported `0.75` are rejected (the
explicit unsupported/contradiction fields override score). These are mocked structured judge
responses. They calibrate decision mechanics only; they do not measure GPT-OSS semantic
accuracy, so the threshold remains a release candidate pending controlled live/human review.

Ordinary runtime traces remain metadata-only and use this hierarchy:

```text
rag_request
  evidence_answerability
  runtime_quality_gate
    groundedness_judge
      bedrock_provider_call
```

Raw questions, answers, evidence, prompts, structured responses, and judge explanations are not
trace attributes or public response fields. Private judge-I/O capture remains limited to the
separate reviewed-dataset workflow and is never enabled for runtime chat.

Online monitoring is disabled by default. Enabling it additionally requires approved data
handling, sampling, concurrency, and daily-spend configuration. It records correlated status
and scores without sensitive raw content and cannot block a completed response.

Offline evaluation runs only from the explicit evaluation action over the reviewed PUBLIC
dataset. RAGAS and MLflow judge execution are not part of normal chat, UI refresh, or tab
navigation. `context_recall` and the existing reference-based `context_precision` are not
scheduled for arbitrary live questions without a reviewed reference.

## Shared accounting rules

The shared cost/usage presentation reports generation, synchronous judge (when one exists),
offline RAGAS, and other known model components independently. It shows model, region,
pricing catalog version/source, measured tokens, real provider invocation count, and
estimated USD with a sub-cent cents equivalent. Unknown usage or unmatched pricing displays
`Cost unavailable`, never zero.

Reasoning tokens are an output-token subset. They are displayed but not added again.
Provider calls are the accounting unit: distinct provider retries remain distinct, while
Instructor parsing retries, provider spans, and parent metric aggregates are not counted as
additional calls. A total is shown only for components in one accounting scope; otherwise
only a known subtotal is shown.

## Local UI verification checklist

1. Start private UI on loopback: `uv run streamlit run app/private_workbench.py --server.address 127.0.0.1 --server.port 8502`.
2. Confirm all six pages and exact tab labels above.
3. Switch through tabs and refresh; confirm no Bedrock/evaluation spinner or new request appears.
4. Submit one approved test question only during a controlled acceptance window; select its
   request, then verify inspector, evaluation-input, execution-trace, and private-call links.
5. Verify missing historical content says unavailable and is not reconstructed.
6. Verify an expired/missing judge artifact is reported safely and a selected artifact can be
   explicitly deleted.
7. Start public UI separately on port 8501; verify a narrow/mobile layout, clickable examples,
   central answer flow, source cards, and the concise production-details expander.
8. Confirm the public source contains no workbench navigation, judge artifacts, evaluation
   execution, administrative operation, environment value, or index mutation action.

## Intentionally unavailable

- MLflow built-in Bedrock automatic judges remain `UNAVAILABLE` after the observed
  `PROVIDER_UNSUPPORTED` result. They are not relabeled completed.
- No automatic MLflow production evaluator is active. A future adapter must satisfy approved
  content handling and the metadata-only trace policy; AI Gateway/deployment requirements must
  be validated first.
- STRICT is implemented but remains a release candidate until the configured threshold is
  calibrated with controlled live GPT-OSS results; mocked fixtures validate policy mechanics,
  not semantic model accuracy.
- No online monitoring worker or alert dispatcher is active in this local deployment.
- Historical raw prompts, context, answers, and judge I/O remain unavailable unless they were
  captured through the existing explicit, expiring reviewed-PUBLIC artifact path.

## One controlled paid acceptance plan (do not run during offline validation)

Set `RAG__QUALITY_POLICY__DEFAULT_PROFILE=STRICT`, keep the configured GPT-OSS Sydney model,
threshold, token caps, zero retries, timeout, and USD 0.01 budget, then start the private
workbench. Submit one reviewed PUBLIC question once. Verify the answer is withheld until the
blocking result completes, the exact request trace has all four hierarchy levels, the provider
call reports actual usage/cost, and generation plus judge costs remain separate. Test one known
grounded case and one deliberately unsupported candidate in a controlled harness; record false
passes/rejections before changing the candidate threshold. Stop on unsupported routing, timeout,
missing pricing/usage, malformed output, correlation mismatch, or budget breach. Do not enable
runtime judge-I/O capture, mutate the index/schema, or automatically regenerate.
